# StoreCalc Authoritative Implementation Contract

Issues: #111, #109

## Status and authority

This is the sole normative source for StoreCalc implementation work after the
consolidation gate. It incorporates the accepted product architecture and every
mandatory correction through the twelfth-pass audit.

This document is still design-only:

- it contains no executable SQL;
- it authorizes no production database, application, account, object-storage,
  worker, secret, DNS, or deployment change;
- the first migration and its database test harness must be designed in a
  separate branch and pull request;
- later feature slices may implement only the requirements and launch gates
  relevant to that slice, but may not contradict this contract.

The earlier StoreCalc architecture, roadmap, schema draft, addenda, and review
passes remain design history. They are not implementation sources. If an old
document differs from this contract, this contract controls.

`MUST`, `MUST NOT`, `REQUIRED`, and `SHALL` are normative. `SHOULD` records a
strong default that needs a documented review before deviation. Requirement IDs
are stable traceability keys and are mapped in
`storecalc-traceability-matrix.md`.

## Product boundary

### SC-FND-001: Core purpose

StoreCalc is a phone-first, privacy-conscious calculator and catalog platform
for facility commissary orders. It supports public anonymous calculation,
private saved work, immutable catalog history, evidence-backed public
maintenance, and bounded owner intervention.

The product does not claim to submit an order to a facility, guarantee live
inventory, guarantee facility acceptance, or prove a user's relationship to a
facility.

### SC-FND-002: Corrected domain spine

The authoritative relationship is:

```text
Facility + audience + calculation context date
  -> evidence-backed program applicability
      -> immutable base catalog version
      -> zero or more compatible immutable scoped profile versions
          -> deterministic resolved configuration and hash
              -> anonymous calculation or authenticated saved order
```

A facility, program, template, version, applicability claim, publication,
profile, resolved configuration, and order are distinct identities.

One program may apply to many facilities. One facility may have several
programs or audiences. One facility may remain on an older catalog while
another adopts a replacement. No name, timestamp, insertion order, or fuzzy
match may silently select among ambiguous valid choices.

### SC-FND-003: Public and private use

Public facility browsing, public template inspection, and authoritative
calculation MUST work without registration. Anonymous state is ephemeral or
explicitly local and is never inserted into persisted order tables.

Authentication is required for server-saved orders, follows, private
facilities, private templates, uploads, proposals, reviews, notifications, and
other user-owned records. Public contribution actions may additionally require
verified email, cooldowns, or reviewed assurance controls.

### SC-FND-004: Historical truth

Published content and completed orders are immutable. Corrections create new
versions or append-only events. Facility merges, catalog identity corrections,
withdrawals, translations, publications, reviews, and applicability changes
MUST preserve their prior history.

### SC-FND-005: Evidence, not popularity

Evidence quality, independence, date, and conflict state govern factual
confidence. Page views, calculations, saved orders, request counts, and other
usage are demand signals only. They MUST NOT increase documentary source counts
or factual confidence.

### SC-FND-006: Delivered slices

StoreCalc SHALL be delivered in bounded slices:

1. authoritative contract and traceability;
2. first bounded schema migration and database test harness;
3. page shell and public facility/template selection;
4. versioned pure calculation core and anonymous calculation;
5. authenticated draft/completed-order persistence;
6. directory and private provisional facilities;
7. immutable public/private templates and publication history;
8. uploads, evidence, extraction drafts, and proposals;
9. community review, applicability review, disputes, and confidence;
10. notifications, jobs, and owner exception tools;
11. reviewed official-source maintenance and international expansion.

Every slice requires focused tests, normal CI, a reviewable pull request,
feature-gated release where needed, and production verification after merge.

## Data and API conventions

### SC-DAT-001: Identifiers

Existing `public.users.id` remains the account identity.

Ordinary StoreCalc relational primary keys use
`integer GENERATED BY DEFAULT AS IDENTITY`. `bigint` is reserved for money,
bounded counters with a documented need, or a reviewed high-volume table.
Sequential database IDs are not authorization secrets.

Public share or download capabilities, when launched, use separate
cryptographically random values. Only a reviewed hash or keyed digest is
stored.

### SC-DAT-002: Money and numeric bounds

Authoritative money is a signed `bigint` count of minor units plus an ISO-style
three-letter currency code and supported minor-unit exponent. Monetary values,
quantities, item counts, rule counts, and payload sizes have explicit upper
bounds before multiplication or allocation.

Server calculation uses JavaScript `BigInt` or an equivalent exact integer
type. JSON and API boundaries serialize values outside JavaScript's safe integer
range as validated base-10 strings. Binary floating point is never
authoritative. Prices, provided funds, limits, subtotals, taxes, and final
totals are nonnegative; only fields explicitly defined as signed differences,
adjustments, or overage/remaining results may be negative.

### SC-DAT-003: Time

Recorded system events use `timestamptz`. Claimed effective dates and intended
order dates use `date`. Facilities use reviewed IANA timezone identifiers.

The system MUST preserve both:

- valid time: the date a source claims a fact became effective; and
- system time: when StoreCalc recorded, published, superseded, or withdrew it.

Late discovery never backdates a StoreCalc publication interval.

### SC-DAT-004: Text and codes

Application boundaries use one documented Unicode normalization version for
search keys and identifiers while preserving original display text. Inputs have
both byte and code-point limits. Control characters and unsafe bidirectional
formatting are rejected from identifiers and short labels.

Country and currency codes use reviewed ISO values. Language tags use reviewed
BCP 47 syntax. Normalized names are search aids, not stable identities.
User-supplied text is escaped on output; any supported rich text uses a strict
allowlist.

### SC-DAT-005: JSON boundary

JSONB may contain only versioned, bounded structures such as canonical
calculation snapshots, proposal diffs, typed rule payloads, notification hints,
confidence factors, or redacted audit snapshots.

JSONB MUST NOT replace core foreign keys, ownership, visibility, order lines,
version lineage, review targets, publication intervals, or state history.
Unknown payload schema versions fail closed.

### SC-DAT-006: Canonical hashes

Every sealed version, profile, proposal diff, resolved configuration, and
completed order records:

```text
content_schema_version
canonicalization_version
hash_algorithm
content_hash
```

The canonical serializer fixes field order, Unicode normalization, numeric
strings, null handling, child ordering, included relationships, and supported
schema version. Proposal hashes bind the template, base version and hash,
candidate version and hash, and diff schema.

### SC-DAT-007: Explicit value states

Unknown, known zero, unlimited, not applicable, and unsupported are different
states. Every field that can be incomplete uses an explicit state contract.

An unknown price cannot be added to an authoritative order. An unknown limit is
not unlimited. Uncertain tax, eligibility, or applicability produces a warning
and prevents an unqualified compliant or confirmed label.

## Database privilege and migration contract

### SC-DB-001: Namespace and role classes

StoreCalc tables live in schema `storecalc`; site-wide account and owner tables
live in `public`.

Executable migrations SHALL resolve the actual configured database principals
and verify four least-privilege role classes:

- migration owner;
- web application runtime;
- bounded asynchronous worker;
- backup/restore operator.

The web and worker roles MUST NOT own schemas, tables, or trigger functions and
MUST NOT receive broad create, alter, drop, bypass-RLS, superuser, or arbitrary
function execution rights.

### SC-DB-002: Functions and grants

Trigger and security-definer functions have an immutable owner, revoked public
execution, explicit grants, and a fixed safe `search_path`. They use no dynamic
SQL derived from user data.

Migrations verify object definitions, owners, grants, constraints, indexes, and
function bodies. Broad `IF NOT EXISTS` is prohibited when it could bless an
incorrect pre-existing object.

### SC-DB-003: Restrictive history relationships

Public facilities, programs, templates, sealed versions, publications,
completed orders, proposals, review events, public evidence, and audit events
use `RESTRICT`/`NO ACTION` or tombstone workflows. Cascades are limited to
clearly private draft aggregates that are deleted together.

### SC-DB-004: Composite lineage

Every child table exposes the parent IDs required for same-parent composite
foreign keys. Existence of four independently valid IDs is never accepted as
proof that those IDs form one valid lineage.

Required candidate keys include the equivalent of:

```text
programs                  UNIQUE (id)
templates                 UNIQUE (id, program_id)
template_versions         UNIQUE (id, template_id)
template_categories       UNIQUE (id, template_id)
template_items            UNIQUE (id, template_id)
version_categories        UNIQUE (id, version_id)
version_buckets           UNIQUE (id, version_id)
version_items             UNIQUE (id, version_id)
version_rules             UNIQUE (id, version_id)
orders                    UNIQUE (id, template_version_id)
```

Executable migrations add every matching composite foreign key described below.

## Accounts, ownership, and high-impact administration

### SC-ACC-001: Additive account security state

The current users table is extended only through reviewed additive migrations:

```text
public.users
  account_status text NOT NULL DEFAULT 'active'
  security_generation integer NOT NULL DEFAULT 1
  disabled_at timestamptz NULL
  disabled_by_user_id integer NULL REFERENCES public.users(id)
  last_login_at timestamptz NULL
```

Allowed account status transitions are serialized. Login, session refresh,
password reset, verification, pending email change, owner recovery, and
federated login all check current account status and security generation.
Reactivation never restores old sessions or tokens.

### SC-ACC-002: Owner is not ordinary admin

The first owner model is a singleton assignment:

```text
public.site_owner_assignment
  singleton_key boolean PRIMARY KEY CHECK (singleton_key)
  owner_user_id integer UNIQUE NOT NULL REFERENCES public.users(id) RESTRICT
  assigned_at timestamptz NOT NULL
  assignment_event_id integer UNIQUE NOT NULL
```

The current owner capability is loaded from PostgreSQL for every sensitive
request. Session role data may show navigation only. The last usable owner
cannot be disabled, demoted, deleted, or stripped of strong authentication
without a transactional ownership transfer.

### SC-ACC-003: Support cases and recovery tokens

```text
public.account_support_cases
  id integer identity PRIMARY KEY
  subject_user_id integer NULL REFERENCES public.users(id) ON DELETE SET NULL
  case_type text NOT NULL
  status text NOT NULL
  opened_by_user_id integer NULL REFERENCES public.users(id) ON DELETE SET NULL
  reason text NOT NULL
  verification_method text NULL
  resolution_summary text NULL
  opened_at timestamptz NOT NULL
  resolved_at timestamptz NULL
  closed_at timestamptz NULL

public.account_recovery_tokens
  id integer identity PRIMARY KEY
  case_id integer NOT NULL REFERENCES public.account_support_cases(id) CASCADE
  token_hash bytea UNIQUE NOT NULL
  expires_at timestamptz NOT NULL
  consumed_at timestamptz NULL
  revoked_at timestamptz NULL
  created_at timestamptz NOT NULL
```

The token target is derived from the support case; a second independently
mutable user ID is not stored. One active token per case is enforced. Expiry,
consumption, and revocation states are coherent. Raw values are emitted once,
never stored or logged.

### SC-ACC-004: Credential-state serialization

Password, email, pending-email, verification, reset, recovery, role, owner,
account-status, strong-factor, and federated-login transitions lock one account
security aggregate and increment `security_generation`.

The committed transition invalidates incompatible tokens and sessions, rotates
the session identifier, writes audit and outbox events atomically, and prevents
an older link from completing afterward.

### SC-ACC-005: Strong owner authentication

Owner email correction, recovery-token issuance, role change, account
disablement, ownership transfer, and factor administration require:

- current database-backed owner authorization;
- active account status;
- CSRF and strict rate limits;
- recent reauthentication;
- a recent strong assertion bound to the session and action class;
- an open bounded support case and explicit reason;
- an idempotency record;
- transactional audit and security-notification intents.

Phishing-resistant authentication such as WebAuthn/passkeys is the preferred
plan. Owner recovery routes MUST NOT launch until the reviewed strong-factor and
backup design exists.

### SC-ACC-006: Audit events and tamper evidence

```text
public.admin_audit_events
  id integer identity PRIMARY KEY
  actor_type text NOT NULL
  actor_user_id integer NULL REFERENCES public.users(id) ON DELETE SET NULL
  target_user_id integer NULL REFERENCES public.users(id) ON DELETE SET NULL
  support_case_id integer NULL REFERENCES public.account_support_cases(id)
  action_type text NOT NULL
  target_type text NOT NULL
  target_id_text text NULL
  reason_code text NOT NULL
  before_snapshot jsonb NULL
  after_snapshot jsonb NULL
  result text NOT NULL
  correlation_id text NOT NULL
  previous_event_hash text NULL
  event_hash text UNIQUE NOT NULL
  created_at timestamptz NOT NULL
  reverses_event_id integer NULL REFERENCES public.admin_audit_events(id)
```

Normal application credentials cannot update or delete audit events. Canonical
event hashes are chained or deterministically batched, and periodic signed
digests are written off-host under a separately controlled identity. Verification
detects missing, reordered, or altered high-impact events.

### SC-ACC-007: Break-glass recovery

Before owner management launches, a repository-owned, checksum-verified,
single-purpose recovery command must exist. It accepts exactly one target, one
allowlisted recovery operation, explicit confirmation, and a bounded reason.
It invalidates sessions and recovery tokens and creates a signed/off-host audit
artifact. It is not arbitrary SQL or a general account editor.

## Contributor privacy identity

### SC-PRV-001: Internal contributor subjects

```text
storecalc.contributor_subjects
  id integer identity PRIMARY KEY
  user_id integer UNIQUE NULL REFERENCES public.users(id) ON DELETE SET NULL
  subject_generation integer NOT NULL DEFAULT 1
  status text NOT NULL
  created_at timestamptz NOT NULL
  anonymized_at timestamptz NULL
```

Public proposals, reviews, requests, support positions, evidence, comments,
translations, and directory/applicability corrections use the internal subject,
not a public username. The subject is not a credential and cannot recover an
email or username.

### SC-PRV-002: Public attribution

```text
storecalc.contributor_public_attributions
  id integer identity PRIMARY KEY
  contributor_subject_id integer NOT NULL
  scope_type text NOT NULL
  facility_id integer NULL
  program_id integer NULL
  template_id integer NULL
  mode text NOT NULL
  public_label text NULL
  created_at timestamptz NOT NULL
  retired_at timestamptz NULL
```

Modes include generic community attribution, scope-specific pseudonym,
deliberately reusable handle, and no author display where policy permits.
Generic or scope-unlinkable attribution is the default for facility-specific
activity. The scope type and exactly-one-or-global null pattern are enforced
with real facility/program/template foreign keys. Internal subject IDs never
appear in public URLs, metadata, feeds, or API output.

### SC-PRV-003: Demand analytics boundary

First-party demand analytics are opt-out, purpose-limited, and bounded to
coarse events such as search, provisional-facility creation, request, upload,
template creation, and completed order. Repeated signals are deduplicated
within a documented window. Raw IP addresses, user-agent fingerprints,
facility names/IDs, private template/order/comment/evidence contents, personal
funds, and current-facility settings are not retained in product analytics or
sent to advertising analytics.

When disclosed and legally permitted, approximate connection country may be
used transiently to prioritize aggregate coverage. It is not proof of identity,
abuse, incarceration, residence, or facility association. A mismatch never
blocks or challenges facility selection and never affects factual confidence.

storecalc.user_settings

storecalc.facility_follows

Follows are private. A facility merge may redirect an active follow through the
classified merge service, but it does not rewrite completed-order or historical
contribution lineage.

The requester cannot add an independent support position. The active position

requester nor supporter account identities. Approval never publishes private
templates, orders, programs, or uploads; the user receives a preview of records
that move, remain private, or need a separate publication proposal.

### SC-DIR-005: Merge behavior

Facility reconciliation classifies records transactionally:

- completed orders, sealed versions, publications, historical proposals,
  evidence links, and audit events keep original lineage;
- settings, follows, eligible private drafts, and unresolved requests may move
  only through explicit reviewed rules;
- completed private orders retain original provenance;
- the duplicate becomes a searchable merged tombstone;
- history records actor, reason, source, destination, time, and correction.

storecalc.assignment_template_applicability

The selection mode explicitly chooses an exact version or a scoped publication;

### SC-APP-004: Applicability history and review

Applicability uses append-only state/evidence events and separate proposal and
review tables:

```text
storecalc.applicability_state_events
storecalc.applicability_evidence
storecalc.applicability_proposals
storecalc.applicability_proposal_state_events
storecalc.applicability_review_events
storecalc.applicability_review_reasons
```

Required columns bind the facility, program, audience, affected interval,
candidate applicability, contributor subject, evidence, hashes, prior event,
and timestamps. Content review and applicability review never share one
confidence value.

### SC-APP-005: Deterministic resolver

Resolver input is:

```text
facility_id
audience_key
calculation_context_date
facility_timezone
viewer scope
supported calculation capabilities
```

Resolver output lists the assignment, applicability, publication or exact
version, base version, profile versions, component hashes, effective intervals,
resolver version, composition version, visibility, warnings, and final hash.

It rejects ambiguous assignments, incompatible profiles, missing dates,
withdrawn or invisible components, unsupported capabilities, and conflicting
same-domain profiles. It never falls back silently.

Deltas are limited to reviewed domains such as tax, spending limits,

content. The first calculator slice may support zero profiles, but MUST reject
rather than ignore a configuration requiring them.

## Templates, catalog identity, and immutable versions

### SC-CAT-001: Templates and forks

```text
storecalc.templates
  id integer identity PRIMARY KEY

## Calculation engine

### SC-CAL-001: One authoritative pure core

Anonymous calculation, saved drafts, completion, proposal previews, review
comparisons, imports, and owner verification call the same versioned pure
calculation core.

The core has no database, locale, clock, or network dependency. Those inputs
are resolved before invocation. Client JavaScript may preview but is never
authoritative.

### SC-CAL-002: Input and output

The server accepts a resolved configuration/hash, explicit context date,
bounded quantities, and optional private available funds. It does not accept
client totals.

Output includes exact lines, item subtotal, tax, final total, every bucket/
constraint result, rule resolution, warnings, validation results, engine and
contract versions, and canonical hash. A later fee component requires its own
reviewed rules and declared calculation capability; the initial core does not
fabricate a zero fee as proof that none applies.

### SC-CAL-003: Composition semantics

Every rule domain declares one behavior such as most-specific override,
additive components, minimum-of-limits, maximum-of-requirements, all-must-pass,
exactly-one, mutually-exclusive, or informational-only.

Same-specificity conflicts without a defined combination are rejected.
Database order, row ID, and insertion order never affect results.

### SC-CAL-004: Capabilities and fail-closed behavior

Each sealed component declares required capabilities. Publication, resolution,
and calculation reject unsupported capabilities. An unsupported or incomplete
configuration is displayed honestly and cannot receive a false ready/compliant
result.

### SC-CAL-005: Context date

Default calculation date comes from the server in the facility timezone.
Historical or future dates are explicit user choices when supported. Drafts
record intended date source and require explicit recalculation/comparison when
date, applicability, publication, or component state changes.

### SC-CAL-006: Personal available funds

One optional private `available_funds_minor` in the order currency is supported.
Null means not provided; a provided value is nonnegative. Remaining or
over-budget funds are a signed exact result derived from funds minus final total
and are kept separate from facility rules. No multi-account balance,
reservation, automatic sync, or currency conversion is implied.

### SC-CAL-007: Validation semantics

Severity is one of:

- `hard_error`: impossible or prohibited under known rules;
- `over_limit`: known facility or personal limit exceeded;
- `warning`: incomplete or uncertain source/rule;
- `informational`: non-blocking explanation.

Drafts may be saved with violations. Completion records the exact result and
does not claim facility acceptance.

### SC-CAL-008: Verification invariants

The calculation suite requires golden fixtures, cross-version reproduction,
property tests, overflow bounds, rule-order randomization, profile
compatibility/conflict tests, unknown-state tests, capability mismatch tests,
aggregate-constraint tests, client/server comparison, and stable hash fixtures.

### SC-ORD-004: Draft concurrency and completion

idempotency key. Completion:

1. locks the draft;
2. verifies ownership, account status, revision, configuration visibility, and
   current lifecycle generations;
3. recalculates with the authoritative core;
4. atomically replaces derived lines, bucket totals, and validation rows;
5. writes provenance/hash metadata;

7. prevents later calculation-content changes.

Funds, account identifiers, internal contributor IDs, private evidence keys,
and audit notes are omitted by default. Spreadsheet-compatible exports
neutralize formula injection. Permanent downloaded files cannot be remotely
revoked; revocable web shares are a separate deferred model.

## Request integrity, authorization, and idempotency

### SC-SEC-001: Viewer-scoped access

Every private query and mutation receives viewer identity and scope. Knowing an
ID is never enough. Unauthorized resources generally produce the same outward
result as nonexistent resources. Counts and pagination are computed only after
authorization filtering. Private component IDs, hashes, conflicts, caches, and
timing do not leak existence.

### SC-SEC-002: Mutation protection

Every state-changing authenticated route uses POST or another intentional
mutation method, CSRF or an equivalently reviewed origin-bound control,
content-type validation, authorization, account-status checks, state-machine
validation, and rate limits. SameSite cookies and Origin/Referer checks are
defense in depth.

Anonymous calculation mutates no server user state but remains bounded and
rate-limited.

### SC-SEC-004: Quotas and pagination

Uploads, extraction, requests, support positions, proposals, reviews, reports,

### SC-SEC-005: Private context outside the database

Private pages use non-shared cache controls. Facility selections, audience,
private IDs, order contents, funds, storage keys, filenames, email addresses,
and contributor subjects are excluded from third-party analytics, URLs,
referrers, ordinary logs, crash payloads, and public cache keys.

Errors use bounded correlation IDs. Notification subjects/previews omit
sensitive facility/order context by default.

### SC-SEC-006: Transport, encryption, and secrets

Before private persistence launches, the release documents and tests TLS for
browser, PostgreSQL, object storage, email, and workers; encryption at rest for
database volumes, object storage, backups, and processing storage; and
least-privilege identities for each service.

Secrets live in managed secret storage, never Git, database rows, logs, or shell
history. The inventory records purpose, consumer, version, rotation,
revocation, and recovery. Historical verification records key/version IDs where
needed. Platform-managed encryption is preferred to custom cryptography.

## State machines and concurrency

### SC-STM-001: Required state services

Text checks restrict vocabulary; transition services enforce legal edges.
Each transition locks the current aggregate, checks expected state and
generation, appends an event/audit row, updates a rebuildable projection, and
uses scoped idempotency.

Required state machines include account, support case, facility request,
assignment/applicability, upload, evidence/artifact, proposal, correction
report, order, publication, notification/outbox, export, and job.

### SC-STM-002: Core transition rules

- Template version: `draft -> sealed`; no reopening.
- Order: `draft -> completed`; archive is metadata; calculation never reopens.
- Proposal: `submitted -> under_review -> accepted|rejected|needs_revision|
  disputed|withdrawn`; a revision is a new candidate.
- Upload: `quarantined -> scanned -> extraction_eligible`; deletion or hold can
  terminate later work.
- Public artifact: `private -> publication_eligible -> public -> withdrawn`;
  withdrawal can be immediate.
- Facility request/support case: only named forward or reviewed reversal edges.
- Publication: append a new non-overlapping interval; never edit history.

Skipped, repeated, and backward transitions fail unless a named append-only
reversal workflow permits them.

### SC-STM-003: Serialized operations

Row/advisory locks and unique constraints serialize version-number allocation,
sealing/submission, publication switches, facility merges, identity events,
applicability resolution changes, order saves/completion, correction
resolution, account security transitions, ownership transfer, account deletion,
retention holds, and migration execution.

  read_at timestamptz NULL

storecalc.notification_preferences
  user_id integer PRIMARY KEY REFERENCES public.users(id) ON DELETE CASCADE
  site_enabled boolean NOT NULL DEFAULT true
  email_enabled boolean NOT NULL DEFAULT true
  accuracy_digest_enabled boolean NOT NULL DEFAULT true
  created_at timestamptz NOT NULL
  updated_at timestamptz NOT NULL
```

Notification types, message keys, hint schemas, and source columns are fixed
allowlists. Exactly one explicit source foreign key is non-null unless the
allowlisted type is a source-free StoreCalc service notice. Hints are bounded
display values, never raw evidence, order contents, funds, email addresses,
tokens, or unrestricted text. Routine accuracy activity is aggregated rather
than producing one message per position. Preferences control ordinary product
site/email delivery only; they cannot suppress essential account-security or
recovery notices.

Product email is an outbox side effect bound to the notification row. At send
time the worker reloads the current verified address, preference, notification
state, account status/security generation, and deletion state.

### SC-NOT-002: Protected security delivery intents

```text
public.security_notification_intents
  id integer identity PRIMARY KEY
  audit_event_id integer NOT NULL REFERENCES public.admin_audit_events(id)
  account_user_id integer NULL REFERENCES public.users(id) ON DELETE SET NULL
  transition_generation integer NOT NULL
  purpose text NOT NULL
  recipient_role text NOT NULL
  destination_ciphertext bytea NOT NULL
  destination_fingerprint bytea NOT NULL
  encryption_key_version text NOT NULL
  state text NOT NULL
  attempt_count integer NOT NULL DEFAULT 0
  created_at timestamptz NOT NULL
  delivered_at timestamptz NULL
  retention_until timestamptz NOT NULL
  redacted_at timestamptz NULL
```

The credential-transition transaction creates one purpose-specific intent for
each required role, such as prior email, replacement email, current owner, or
incoming owner. Exact destinations use managed-key envelope encryption and a
separately granted protected table; ordinary web, StoreCalc, analytics, and
generic outbox readers cannot decrypt them. State transitions are allowlisted,
append an audit event, and retain only bounded delivery metadata after the
policy deadline. Security notices do not consult optional StoreCalc
preferences.

### SC-ASY-001: Outbox and job tables

```text
public.outbox_events
  id, event_type, aggregate_type, aggregate_id, aggregate_generation,

  attempt_count, next_attempt_at, created_at, delivered_at, dead_lettered_at

public.async_jobs

```

Fixed types and schemas are allowlisted. Payloads contain IDs, versions, hashes,
and bounded hints, not funds, raw documents, sessions, tokens, or unrestricted
text.

### SC-ASY-002: Execution-time authorization

Before every side effect, workers reload authoritative state, authorization,
visibility, lifecycle/security generations, cancellation, supersession, and
holds. Possession of a job row is not authorization.

Writes use expected-state/generation conditions. Losing a deletion/withdrawal
race removes temporary output and records cancellation. Retries repeat the
same validation.

### SC-ASY-003: Non-resurrection

Extraction, artifacts, translations, projections, exports, search indexes,
caches, thumbnails, imports, and backups created after a deletion cutoff cannot
recreate deleted, anonymized, quarantined, or withdrawn information.

Restore/replay processes withdrawal/deletion events before publishing derived
state. Projection rebuilds preserve distinct retained pseudonymous subjects but
cannot reconstruct deleted account links.

### SC-ASY-004: Security notification recipients

Sensitive account transitions create the SC-NOT-002 purpose-specific recipient
intents. Necessary exact destination snapshots live only in that protected
delivery table with explicit access, encryption, retention, and redaction, not
a generic outbox payload.

Workers verify the transition and do not silently substitute the account's
latest address.

### SC-ASY-005: Status and dead letters

User-visible state distinguishes committed core data from pending, delivered,
failed, cancelled, superseded, or dead-lettered secondary work. Queued does not
mean sent or published.

Dead letters are visible to bounded owner/operations screens with safe retry.
Safety-critical withdrawal and cache invalidation escalate after a defined
bound. Retry preserves original intent and idempotency.

## Privacy, deletion, retention, and holds

### SC-DEL-001: Data classes

Account deletion explicitly classifies:

- delete: private facilities/programs/templates/drafts, raw uploads,
  extraction drafts, saved orders, follows, settings, notifications, and
  unnecessary support text;
- preserve with direct account link removed: accepted public facts, sealed
  public versions, approved public evidence metadata, append-only proposal/
  review/applicability history, publication/state history, and minimized audit;
- delete/redact: comments, explanations, filenames, free text, derived trust,
  analytics, and recipient snapshots according to policy.

No blanket cascade may erase sealed public history.

### SC-DEL-002: Deletion transaction

Deletion locks the account/security aggregate and relevant contributor subject,
classifies rows, revokes sessions/tokens, applies formal holds, removes private
objects, anonymizes retained history, emits cleanup jobs/outbox events, and
verifies unrelated users remain untouched.

The current YouList deletion helper MUST be replaced or extended before
StoreCalc persistence launches.

### SC-DEL-003: Retained pseudonymous history

Retained events preserve only the contributor subject continuity needed for
duplicate-position and audit integrity. Re-registration does not inherit prior
trust and does not automatically gain another weighted position.

Retention duration and deletion disclosure are defined before public review
launch.

### SC-DEL-004: Bounded holds

```text
public.data_retention_holds
  id, hold_type, subject_user_id, contributor_subject_id, support_case_id,
  evidence_id, public_artifact_id, template_version_id, content_report_id,
  actor_type, actor_user_id, reason_code, created_at, review_at, expires_at,
  released_at, audit_event_id
```

Every target column has a real foreign key and exactly one is non-null. Holds
are fixed-purpose, time-bounded, audited, and retain only necessary data. They
do not retain private orders/funds merely because the account contributed
public facts. Release resumes deletion/redaction idempotently.

### SC-DEL-005: Backup retention

Deletion disclosure explains encrypted-backup retention and expiry. A restore
does not bypass a later deletion, anonymization, artifact withdrawal, or hold
release event.

## Route and authorization contract

### SC-ROU-001: Public routes

Public GET routes cover StoreCalc home, country/facility search, public program/
template/version/applicability inspection, and bounded confidence/evidence
summaries. Public POST calculation accepts only bounded quantities and context
and creates no persisted user record.

Private IDs are absent from public counts, errors, pagination, and caches.

### SC-ROU-002: Authenticated private routes

Saved orders, settings, follows, private facilities/programs/templates,
uploads, extraction drafts, notifications, and exports require current account
status, viewer-scoped queries, CSRF on mutations, revision/idempotency where
applicable, and private cache headers.

### SC-ROU-003: Public contribution routes

Facility requests, public proposals, weighted reviews, public evidence,
comments, translations, and applicability changes require current contribution
assurance, contributor subject, CSRF, rate/volume limits, self-amplification
checks, and privacy-preserving attribution preview.

### SC-ROU-004: Owner routes

Owner account support and recovery use the full SC-ACC-005 gate. StoreCalc
moderation may later be delegated separately and never inherits account-recovery
authority automatically.

The account action allowlist is limited to: open/resolve a support case; correct
an approved username or initiate the reviewed verified-email correction flow;
correct the current StoreCalc facility/assignment setting at the user's
documented request; restart email verification; issue a single-use recovery
link; suspend or reactivate an account; revoke sessions and recovery tokens;
transfer the singleton owner assignment; place or release a formal hold; and
inspect redacted audit, security-notice, and job status.

Read-only owner search accepts exact username, email, or internal user ID and
returns bounded account status, verification/role state, registration and last
login time, active-session count, current owner assignment, support cases, and
prior administrative actions. Access to private StoreCalc context requires the
open support case whose requested correction needs it; it is never available
through bulk search or analytics.

After their own feature gates pass, StoreCalc exception routes may: decide a
facility request; apply a classified facility merge or reviewed identity/fact
event; resolve an abuse/privacy/security report; quarantine or withdraw unsafe
evidence; withdraw an unsafe catalog/configuration from new use; resolve a
disputed proposal or applicability claim through its state machine; and safely
retry or cancel an allowlisted dead-letter job. Routine catalog correction
continues through public proposal/review workflows and does not require owner
approval. Deferred import tooling grants no action until separately reviewed.

Each account or exception action class is separately enabled and uses a named
route and domain service, current database authorization, recent strong
authentication proportional to impact, CSRF, expected state/generation,
scoped idempotency, a bounded reason, transactional audit, and required
security notices. There is no generic account/entity patch route.

No route exposes arbitrary SQL, password hashes, session IDs, token values,
private raw documents, direct password setting, silent impersonation, or an
unreviewed StoreCalc moderation power.

## Accessibility, mobile resilience, search, and language

### SC-UX-001: Accessibility

Core flows use semantic controls, full keyboard operation, visible focus,
screen-reader status announcements, direct numeric quantity input, linked error
summaries, text in addition to color, practical touch targets, zoom/reflow,
contrast, reduced motion, and linear alternatives to side-by-side diffs.

Automated checks are supplemented by keyboard and screen-reader acceptance
tests.

### SC-UX-002: Unreliable mobile networks

Payloads are small and deterministic, catalogs paginate/progressively render,
mutations show pending/committed/failed state, retries are idempotent, stale
versions are explicit, and long editing workflows do not depend on one open
request. Uploads are safely restartable or resumable with checksums.

### SC-UX-003: Search disambiguation

Facility/template search shows jurisdiction, agency, locality, status, former
names, alias/fuzzy-match labels, and audience. Ambiguous matches require user
selection. Closed/renamed/merged identities point to current context without
erasing history. Ordering is deterministic and does not imply endorsement.

### SC-UX-004: Honest public language

The UI distinguishes catalog confidence, applicability confidence, source/effective
date, warnings, unsupported rules, current publication, and facility
acceptance/live stock. Terms such as official, verified, available, accepted,
or submitted require explicit definitions and documented factual support.

## Operations, recovery, and deployment

### SC-OPS-001: Migration package

Every migration package includes immutable SQL, checksum, expected object
definitions, database tests, role/grant verification, lock and statement
timeouts, estimated lock behavior, forward compatibility, and rollback/forward
repair plan.

Only one migration runs at a time under a deployment/advisory lock. Migration
code is privileged repository-owned software.

### SC-OPS-002: Rehearsal and backup

Before production:

1. verify merged commit and migration checksum;
2. create and verify a fresh off-VM backup;
3. restore to a disposable PostgreSQL instance;
4. apply the migration under production-like roles;
5. run schema, constraint, ownership, grant, service, and deletion tests;
6. exercise safe rollback when tables are still empty;
7. verify the original fingerprint after rollback;
8. record runtime and lock behavior.

### SC-OPS-003: Expand-contract and feature gates

Schema expands before dependent routes activate. Application overlap is
compatible with old and new capability states. Server feature gates remain off
until exact schema verification passes. A capability/readiness check reports
safe availability without leaking schema details.

Rollback disables the feature or restores compatible code; it does not drop
live data. Cleanup migrations wait until no deployed code uses the old shape.

### SC-OPS-004: Production execution boundary

The current controlled Ops migration action supports only a narrow index
operation. StoreCalc migrations require either a separately reviewed exact
repository-owned migration capability or one bounded manually supervised run
with the same checksum, backup, rehearsal, transaction, and verification
controls.

Generic SQL, shell access, or migration text supplied at runtime is forbidden.

### SC-OPS-005: Recovery and observability

Monitoring covers outbox/jobs/dead letters, stuck quarantine, evidence-object
reconciliation, imports/source checks, projection rebuilds, hash mismatches,
withdrawal propagation, cache invalidation, backup freshness, restore tests,
and schema/capability mismatches.

Logs and alerts contain correlation IDs and bounded metadata only. Restore
ordering preserves privacy, deletion, withdrawal, and object scope.

## Deliberately deferred capabilities

### SC-DEF-001: Deferred product/calculation features

The following are not silently assumed by initial slices:

- recurring weekly/monthly limits and prior-purchase ledgers;
- multiple personal funding accounts, reservations, or automatic balance sync;
- foreign-exchange conversion;
- additive multi-component tax groups beyond one resolved treatment;
- facility/service fee rules until a reviewed fee capability exists;
- live inventory, facility order submission, or acceptance confirmation;
- scheduled future publication;
- public/revocable order sharing;
- automatic offline multi-device synchronization.

### SC-DEF-002: Deferred platform features

Also deferred until separately reviewed:

- exact OCR/extraction provider;
- arbitrary external-source retrieval;
- automatic official-source importers, staging tables, and monthly timer;
- general RBAC beyond current role plus explicit owner capability;
- database row-level security;
- support-session impersonation;
- trigram/full-text extensions;
- partitioning or archival tables before measured need;
- advanced reusable rich text;
- automatic machine-translation publication.

Deferred means absent behind a clear capability boundary. It never means
partially supported or guessed.

## Launch gates

### SC-GAT-001: Anonymous calculator gate

Requires a supported sealed catalog fixture, authoritative calculation core,
capability rejection, exact money/tax/limit tests, bounded anonymous endpoint,
accessible/mobile UI, honest status language, and no persistence dependency.

### SC-GAT-002: Saved-order gate

Requires migrations through order validation tables, viewer-scoped services,
CSRF, idempotency, optimistic revisions, account status/security generation,
completed-order sealing, deletion coverage, private cache/log rules, encryption
and backup verification.

### SC-GAT-003: Public contribution gate

Requires contributor subjects and attribution, assurance policy, immutable
proposals, append-only reviews, evidence independence, self-amplification
prevention, rate/volume limits, abuse reports, deletion/anonymization policy,
and precise public status language.

### SC-GAT-004: Upload/evidence gate

Requires private object storage, quarantine/scanning, active-content isolation,
privacy and redistribution review, explicit public artifacts, lifecycle
generations, execution-time job validation, object/database recovery manifest,
withdrawal/cache invalidation, and encrypted backup restore tests.

### SC-GAT-005: Owner support gate

Requires explicit singleton owner capability, strong authentication, current
database authorization, credential serialization, session/token invalidation,
support cases, hashed recovery tokens, scoped idempotency, durable security
notices, append-only plus off-host tamper-evident audit, last-owner protection,
formal holds, and bounded break-glass recovery.

### SC-GAT-006: Scoped profile gate

The first release may resolve a complete single catalog version only. Profile
composition activates only after immutable profile schema, compatibility,
domain-specific composition, component visibility, dependency withdrawal,
resolver/hash fixtures, and ambiguity tests pass. Until then, configurations
requiring a profile are unsupported and fail closed.
