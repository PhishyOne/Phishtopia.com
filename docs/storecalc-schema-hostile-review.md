# StoreCalc Schema Hostile Review

> Historical review record. Its accepted corrections are consolidated in
> `storecalc-implementation-contract.md`; this file is not an implementation
> source.

Issues: #111, #109

Status: mandatory design corrections discovered during the second architecture review.

This document supplements `storecalc-schema-design.md` and `storecalc-schema-integrity-addendum.md`. Executable migrations must satisfy all three documents. Where this review is stricter, this review controls.

The review assumes application code will eventually contain bugs, requests will be retried from unreliable mobile connections, two users may act concurrently, and privileged routes may be called with stale session data. Database and service boundaries must remain correct under those conditions.

## 1. Use practical identifier types deliberately

The existing `public.users.id` is an integer identity, and Phishtopia is not expected to approach 2.1 billion rows in any StoreCalc identity table.

For the first implementation:

- prefer `integer GENERATED BY DEFAULT AS IDENTITY` for ordinary relational IDs;
- reserve `bigint` for monetary values, counters that can realistically exceed integer range, or a table with a documented high-volume reason;
- do not introduce `bigint` IDs merely for appearances.

This avoids unnecessary node-postgres behavior where `int8` values arrive as strings and prevents accidental conversion through JavaScript `Number`.

Authoritative money arithmetic still uses integer minor units and must use JavaScript `BigInt` or another exact integer implementation. API and JSON boundaries serialize large monetary values as validated decimal strings because native JSON cannot encode JavaScript `BigInt`.

Every calculation path must enforce bounded quantities and values before multiplication so hostile inputs cannot create unreasonable CPU, memory, or database work.

## 2. Separate governing and physical directory lineage

One `jurisdiction_id` is insufficient for facilities.

A federal facility may be physically located in a state or province while being governed by a national agency. The directory therefore distinguishes:

- the agency's governing jurisdiction;
- the facility's physical country and physical jurisdiction;
- optional lower-level locality text.

The first normalized shape should use concepts equivalent to:

```text
agencies
  id
  country_id
  governing_jurisdiction_id

facilities
  id
  physical_country_id
  physical_jurisdiction_id
  agency_id
```

Required lineage constraints include:

```text
(jurisdiction.parent_jurisdiction_id, jurisdiction.country_id)
  -> jurisdictions(id, country_id)

(agency.governing_jurisdiction_id, agency.country_id)
  -> jurisdictions(id, country_id)

(facility.physical_jurisdiction_id, facility.physical_country_id)
  -> jurisdictions(id, country_id)
```

A facility's agency may have a different governing jurisdiction from the facility's physical jurisdiction, but both must belong to coherent countries according to the supported model.

Jurisdiction parent relationships and facility merge relationships must reject self-links and cycles. Cycle prevention is a mandatory trigger or transactionally locked recursive check, not only a service convention.

## 3. Facility merges must not rewrite history

A facility merge is identity reconciliation, not a bulk rewrite of every historical row.

The merge service must classify records:

- completed orders keep their original facility, program, template, version, and snapshots;
- sealed public versions and publication history keep their original lineage;
- historical proposals, reviews, evidence links, and audit events are not reparented silently;
- current user settings, follows, private drafts, unresolved requests, and other explicitly movable records may be redirected transactionally;
- the duplicate facility becomes a merged tombstone pointing to the canonical facility;
- lookups resolve the canonical target while historical pages can still explain the original identity.

Merge pointers must be acyclic. A merge history/event table records actor, reason, source, destination, time, and reversal or corrective action. Ordinary routes never delete a merged or historically referenced public facility.

The same principle applies later to duplicate programs or templates: use explicit supersession/merge history instead of silently changing published ancestry.

## 4. Support overlapping spending limits

A single `version_items.spending_bucket_id` cannot represent common rule combinations such as:

- every item counts toward the overall commissary limit;
- electronics also count toward a smaller electronics cap;
- phone credits use a separate limit and do not count toward the main limit;
- a tax-exempt item still counts toward one or more spending limits.

Replace the single authoritative bucket foreign key with a many-to-many relationship equivalent to:

```text
version_item_bucket_memberships
  version_item_id
  version_id
  spending_bucket_id
  membership_type
  primary_display boolean
```

Composite foreign keys enforce one version. Each item may count toward zero, one, or several limit buckets.

`membership_type` must have defined calculation semantics. The initial vocabulary should distinguish at least:

- counts_toward;
- excluded;
- informational_only.

Exactly one membership may be the primary display grouping when the interface needs one. Display grouping does not control limit arithmetic.

A null bucket limit means explicitly unlimited. Unknown limits remain warnings and never become unlimited by accident.

## 5. Define quantity semantics precisely

Zero quantity must remain a valid "not selected" state even when a selected item has a minimum purchase quantity.

Do not use an ambiguous `quantity_min` rule that appears to prohibit zero. Prefer concepts equivalent to:

```text
minimum_selected_quantity
maximum_order_quantity
quantity_step
```

Validation is:

```text
quantity = 0
OR
quantity >= minimum_selected_quantity
AND quantity <= maximum_order_quantity when present
AND (quantity - minimum_selected_quantity) follows quantity_step
```

The first release treats these as limits for one calculated order. Weekly, monthly, account-balance, or institution-enforced historical limits require explicit period and ledger semantics and must not be inferred from an order-only rule.

## 6. Make tax behavior reproducible, not merely precise

`rate_ppm` and `rounding_mode` are not enough to reproduce every result.

Every version and order must snapshot:

- currency code;
- currency minor-unit exponent;
- tax rate;
- inclusive or exclusive pricing;
- rounding mode;
- rounding scope, such as per unit, per line, category subtotal, or order subtotal;
- tax calculation/canonicalization version.

The initial implementation should support one effective combined tax rule per item after specificity resolution. It must not silently stack multiple matching tax rules.

If additive state, county, municipal, or special tax components are later supported, introduce explicit tax-component groups and ordering rather than changing the meaning of existing rows.

Required checks include a documented valid range for `rate_ppm`, allowed currency exponents, nonnegative monetary fields, and overflow-safe exact integer arithmetic.

## 7. Version hashes need a defined format

A bare `content_hash` cannot be verified forever unless its canonical representation is defined.

Template versions, proposal diffs, and completed-order snapshots must record concepts equivalent to:

```text
content_schema_version
canonicalization_version
hash_algorithm
content_hash
```

The canonical serializer defines field order, text normalization, numeric representation, child-row ordering, null handling, and included relationships.

A proposal also binds its diff to:

- template ID;
- base version ID and content hash;
- candidate version ID and content hash;
- diff schema version;
- diff hash.

A stale diff can therefore never be submitted after either side changes.

## 8. Seal completed orders

Template versions are not the only historical records requiring immutability.

Orders have two phases:

- draft: editable with optimistic concurrency;
- completed: sealed and immutable.

Draft orders require a monotonically increasing `revision` value. Every mutation supplies the expected revision and fails on conflict instead of overwriting changes from another tab, device, retry, or stale page.

Completion transactionally:

1. locks the draft;
2. recalculates from the sealed template version;
3. replaces all derived lines and bucket totals;
4. records engine/schema/hash metadata;
5. stores facility, program, template, version, source-date, currency, and display-name snapshots;
6. marks the order completed;
7. permanently blocks changes to calculation content and child rows.

Archiving, revoking a share link, or attaching a user-visible note may remain mutable metadata. Calculation content does not.

Repeated mobile submissions use an idempotency key or the same expected revision so completion cannot create duplicate orders or apply twice.

## 9. Preserve review history as events

A community review must not be silently rewritten by updating one mutable verdict row.

Use append-only review events or revisions plus a rebuildable current-position projection. The event history records:

- reviewer subject;
- verdict;
- structured reasons;
- evidence references;
- creation time;
- superseded/retracted relationship;
- proposal candidate/base hashes reviewed.

Changing from `accurate` to `needs_correction` creates a new event. It does not erase the earlier position.

The rule requiring at least one structured reason for `needs_correction` is mandatory database enforcement through a deferred constraint trigger or an equivalent atomic design. "If practical" is not sufficient.

A contributor may not add a confidence-weighted review to their own proposal. They may comment, explain, revise, or submit evidence. Resolved proposals reject new ordinary reviews; later evidence uses a correction report or new proposal.

Correction-report and proposal state changes also need append-only state events or complete audited transitions.

## 10. Fix derived contributor scope keys

A primary key containing `store_program_id` makes that column implicitly non-null, so the conceptual `contributor_scope_stats` table cannot also represent facility-only contributions as written.

Use one of these explicit designs:

- separate facility-scope and program-scope summary tables; or
- a validated `scope_type` plus `scope_id` model with a strict target allowlist and rebuild tests.

Do not use a nullable foreign key inside a primary key as an accidental polymorphic scope.

The derived table grants no permission. Deleting or rebuilding it must not affect factual review history.

## 11. Enforce current-setting and upload lineage

Composite lineage checks also apply outside orders.

At minimum, executable migrations must prevent:

- `user_settings.current_store_program_id` from belonging to another facility than `current_facility_id`;
- an upload's store program from belonging to another facility than the upload's facility;
- a proposal or correction reason from targeting a version outside its declared template/proposal sides;
- a private facility, program, template, evidence record, or upload from being referenced by another user without an approved publication/copy workflow.

Where privacy ownership cannot be represented by an ordinary foreign key, the service uses locked validation and tests. No generic "fetch by ID" query may return private StoreCalc records without viewer identity and scope checks.

## 12. Separate private uploads from public evidence rigorously

Raw uploads begin quarantined and private.

Upload state must distinguish:

- file-type/security scan;
- extraction processing;
- personal-information review;
- publication eligibility;
- deletion/object-retention state.

Never serve original uploads inline from a public origin. Validate actual file signatures, size, page/image limits, and decompression bounds rather than trusting filenames or client MIME types.

A public evidence artifact is a separately generated or reviewed object. Public versions never link directly to another user's private storage key.

Public evidence also needs withdrawal/tombstone state. If personal information or malicious content is discovered later, the artifact may be revoked while preserving the minimum hash, relationship, reason, and audit history needed to explain the template decision.

User-supplied source URLs are data. The application must not fetch arbitrary URLs synchronously. Any future retrieval worker requires SSRF defenses, protocol/host validation, redirect limits, size/time limits, and private-network blocking.

## 13. Do not ship an unvalidated polymorphic report target

`content_reports(target_type, target_id)` has no ordinary foreign-key integrity.

The executable design must choose one of:

- explicit nullable foreign keys for each supported report target with an exactly-one-target check; or
- a mandatory trigger using a fixed target allowlist, locked search path, visibility validation, and deletion behavior.

A comment saying a trigger "may" validate the target is insufficient. Orphaned or cross-private reports would break moderation and could leak record existence.

## 14. Harden owner authorization beyond the current middleware

The current `requireAdmin` middleware trusts `req.session.user.role`. That is acceptable for ordinary navigation gating but insufficient for account recovery, role changes, disabling accounts, session invalidation, or recovery-token issuance.

Sensitive owner actions must:

- load the actor's current role and account status from PostgreSQL on every request;
- require a recent reauthentication timestamp tied to the session;
- use CSRF protection and a strict rate limit;
- reject stale or disabled sessions;
- prevent an administrator from disabling, demoting, or deleting the last usable administrator;
- require an explicit reason and bounded support case;
- use an idempotency/request identifier so a retried mobile form does not apply twice;
- append the audit event in the same database transaction as the state change.

Session-cached role data may control whether a link is shown. It is not the final authorization source.

Recovery-token constraints must prove that the token's user matches the support case's target user. Prefer deriving the user from the case or use a composite foreign key. Enforce expiry after creation, one active token per case/user, and mutually coherent consumed/revoked states.

## 15. Use a durable outbox for post-commit side effects

Email, object deletion, notification delivery, and similar network work must not occur inside a PostgreSQL transaction.

Sensitive workflows write a bounded outbox event in the same transaction as the account/template/order change. A retry-safe worker delivers it afterward.

Outbox events require:

- fixed event types;
- bounded non-secret payloads;
- idempotency keys;
- attempt count and next-attempt time;
- delivered/dead-letter state;
- retention and redaction rules.

This is especially important when notifying old and new email addresses after owner-assisted recovery. A successful database change must not become invisible because an SMTP request failed after commit.

## 16. Prefer restrictive deletion on historical parents

Do not rely only on a trigger to rescue broad parent cascades.

For facilities, public programs, public templates, sealed versions, publications, completed orders, proposals, reviews, and public evidence, use `RESTRICT`/`NO ACTION` relationships or explicit tombstone workflows wherever historical records must survive.

Cascades remain appropriate for clearly private/draft-owned children that are deleted as one bounded aggregate.

The account-deletion service explicitly classifies rows. It must not trigger a chain capable of deleting sealed public history.

## 17. Prevent overlapping publication history

The one-current-publication partial unique index prevents two open rows, but it does not prevent overlapping closed historical intervals.

Publication rows require:

- `ended_at IS NULL OR ended_at > started_at`;
- serialization when switching the current publication;
- database enforcement that periods for one template do not overlap, using a trigger or an exclusion strategy reviewed for operational compatibility;
- a sealed, same-template version;
- append-only publication periods.

Backdated corrections use explicit corrective events and cannot silently rewrite prior intervals.

## 18. Treat migration code as privileged software

Executable migrations must define more than tables and constraints.

They must also define and test:

- schema/table/function ownership;
- least-privilege grants for the application role;
- trigger-function owners and a fixed safe `search_path`;
- no dynamic SQL derived from user data;
- advisory or deployment locking so two migration runs cannot overlap;
- bounded `lock_timeout` and `statement_timeout` values;
- exact object-definition verification after migration;
- checks that reject an existing object with the right name but wrong definition.

Avoid broad `IF NOT EXISTS` use that can make a partially wrong schema look successful.

Indexes on empty/new tables can be created transactionally. Any later `CREATE INDEX CONCURRENTLY` work must be isolated because PostgreSQL forbids it inside a transaction block.

## 19. Required additional tests

Before executable migrations are accepted, tests must attempt and reject:

- a jurisdiction parent from another country;
- a jurisdiction or facility merge cycle;
- a facility whose physical jurisdiction belongs to another country;
- rewriting completed-order calculation content;
- saving a stale draft revision;
- double-completing an order through a retried idempotency key;
- an item that should count toward both main and category limits being counted only once;
- treating an unknown limit as unlimited;
- ambiguous or silently stacked tax rules;
- a review changing verdict without preserving the prior event;
- a proposer casting a weighted review on the proposer's own proposal;
- a user setting or upload combining unrelated facility/program IDs;
- a public version referencing quarantined/private evidence;
- an orphaned or invisible content-report target;
- a recovery token targeting a different user than its support case;
- a stale session role authorizing an owner action;
- two overlapping publication intervals;
- a parent cascade deleting sealed public history.

## Result

With these corrections, the core spine remains:

```text
Facility -> Store program -> Template -> Immutable template version -> Sealed order
```

The corrected design also acknowledges two additional truths:

```text
One item may participate in several simultaneous limits.
Community trust is historical evidence, not a mutable vote counter.
```

No executable SQL should be written until these requirements are reflected in the migration plan and test matrix.
