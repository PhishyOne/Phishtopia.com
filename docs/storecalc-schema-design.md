# StoreCalc Schema and Migration Design

Issues: #111, #109

## Status

Design only. This document does not contain an executable production migration.

The first implementation migrations must be created separately, rehearsed against a disposable PostgreSQL database, reviewed through CI, backed up before production, and applied only through the approved deployment path.

## Existing Phishtopia constraints

StoreCalc must extend the current application rather than replace working account infrastructure.

Current relevant behavior includes:

- users are stored in `public.users` with existing integer IDs;
- the existing role field supports `user` and `admin`;
- pending email changes currently live on `public.users`;
- sessions are stored in `public.session` through `connect-pg-simple`;
- YouList ownership references the existing user ID;
- account deletion explicitly removes sessions and user-owned YouList rows in one transaction;
- current migration files are additive transactional SQL under `migrations/`;
- the controlled Ops migration worker currently supports only a narrow index operation and cannot be treated as a generic migration runner.

StoreCalc therefore preserves `public.users.id` as the account identity and introduces new tables incrementally. It does not rename, recreate, or bulk-copy the existing users table.

## Design principles

1. **Dedicated namespace.** StoreCalc tables belong in a `storecalc` PostgreSQL schema.
2. **Stable identities.** Facility, program, template, category, and item identities survive name and version changes.
3. **Immutable published content.** Submitted template content is sealed. Corrections create new versions.
4. **Historical reproducibility.** Saved orders preserve the exact prices, rules, currency, and totals used at creation.
5. **Privacy by default.** Private facilities, templates, orders, follows, drafts, and settings are never exposed by merely knowing an ID.
6. **Evidence before popularity.** Reviews are structured signals attached to specific versions or proposals.
7. **Scoped trust.** Contributor history is limited to relevant facilities, programs, and contribution types.
8. **Bounded administration.** Owner account support and moderation are audited workflows, not arbitrary SQL or silent impersonation.
9. **Incremental migration.** Initial migrations are additive and independently deployable.
10. **Application and database validation.** Application checks improve errors; database constraints protect invariants.

## PostgreSQL conventions

### IDs

Use `bigint GENERATED BY DEFAULT AS IDENTITY` for internal relational identities.

Sequential IDs are not secrets. Every read and mutation still performs server-side visibility, ownership, role, and state checks. Public share links use separate random tokens whose raw values are never stored.

### Time

Use `timestamptz` for recorded times. Effective calendar dates such as a store-sheet effective date use `date` when no time-of-day meaning exists.

### Money

Use signed `bigint` minor units with nonnegative checks for prices, limits, subtotals, taxes, and totals. Store an explicit ISO 4217-style three-letter currency code on each version and order.

The calculator must not use binary floating point for authoritative currency calculations.

### Tax rates

Store tax rates as integer parts per million (`rate_ppm`).

Examples:

```text
7.25%   = 72,500 ppm
7.125%  = 71,250 ppm
```

Each tax rule also records its rounding mode and whether the listed price is tax-inclusive. The calculation service owns the supported rounding vocabulary and tests every mode.

### Status values

Prefer `text` columns with named `CHECK` constraints over PostgreSQL enum types. Text checks are easier to extend through reviewed additive migrations.

### Names and case-insensitive uniqueness

Follow the current project convention of text plus `LOWER(...)` indexes rather than adding an extension merely for case-insensitive text.

### JSONB boundary

JSONB is allowed for:

- immutable order calculation snapshots;
- generated proposal diffs;
- versioned rule metadata that has a strict application schema;
- notification payloads containing only bounded identifiers and display hints;
- sanitized administrative before/after snapshots;
- confidence-factor explanations tied to an algorithm version.

JSONB must not replace core foreign keys, item rows, facility ownership, template-version relationships, reviews, or order lines.

## Site-wide account support tables

These tables live outside the StoreCalc schema because owner-assisted recovery applies to the entire site.

### `public.account_support_cases`

Purpose: record a bounded owner support or account recovery workflow.

Suggested columns:

```text
id bigint identity primary key
user_id bigint not null references public.users(id)
case_type text not null
status text not null
opened_by_user_id bigint not null references public.users(id)
reason text not null
verification_method text
resolution_summary text
opened_at timestamptz not null
resolved_at timestamptz
closed_at timestamptz
```

Constraints:

- `case_type` initially allows email correction, verification restart, account recovery, disable/reactivate, session invalidation, and another reviewed bounded type;
- `status` initially allows open, awaiting_user, approved, completed, rejected, and closed;
- reason and resolution fields have strict length limits;
- a case never stores passwords, password hashes, raw tokens, cookies, identity-document images, or unrestricted request bodies.

### `public.account_recovery_tokens`

Purpose: support short-lived single-use owner-assisted recovery without owner-selected permanent passwords.

Suggested columns:

```text
id bigint identity primary key
case_id bigint not null references public.account_support_cases(id)
user_id bigint not null references public.users(id)
token_hash bytea not null unique
expires_at timestamptz not null
consumed_at timestamptz
revoked_at timestamptz
created_at timestamptz not null
```

Only a cryptographic hash is stored. The raw recovery value is displayed or sent once and cannot be recovered from the database.

### `public.admin_audit_events`

Purpose: append-only record of sensitive owner actions.

Suggested columns:

```text
id bigint identity primary key
actor_user_id bigint references public.users(id) on delete set null
target_user_id bigint references public.users(id) on delete set null
support_case_id bigint references public.account_support_cases(id)
action_type text not null
target_type text not null
target_id_text text
reason text not null
before_snapshot jsonb
after_snapshot jsonb
result text not null
created_at timestamptz not null
reverses_event_id bigint references public.admin_audit_events(id)
```

The table is append-only through application rules and a database trigger. Updates and deletes are rejected outside a separately reviewed emergency repair procedure.

Snapshots contain only approved fields. Password hashes, tokens, cookies, session contents, private orders, and raw uploaded documents are prohibited.

### Additive user fields

A later account-support migration may add bounded fields to `public.users`:

```text
account_status text not null default 'active'
disabled_at timestamptz
disabled_by_user_id bigint references public.users(id)
last_login_at timestamptz
```

The first version should preserve the current `role IN ('user', 'admin')` model. A generalized role-assignment system is unnecessary until a real non-owner permission requirement exists. StoreCalc community trust is not implemented through global account roles.

### `storecalc.facilities`

Both canonical public facilities and immediately usable private provisional facilities use stable records in the same table.

```text
id bigint identity primary key
country_id bigint not null references storecalc.countries(id)
jurisdiction_id bigint references storecalc.jurisdictions(id)
agency_id bigint references storecalc.agencies(id)
record_scope text not null
owner_user_id bigint references public.users(id)
official_name text not null
native_name text
facility_type text
physical_region text
locality text
status text not null
merged_into_facility_id bigint references storecalc.facilities(id)
created_by_user_id bigint references public.users(id) on delete set null
created_at timestamptz not null
updated_at timestamptz not null
```

Key checks:

- `record_scope` is public or private;
- private facilities require `owner_user_id`;
- public facilities must not have a private owner;
- merged records require `merged_into_facility_id` and cannot merge into themselves;
- only private facility owners and administrators can read private records;
- deletion of a user cascades private provisional facilities but does not delete canonical public facilities they helped create.

Facility merging is a transactional service operation. It reassigns allowed child records, preserves history, and marks the duplicate as merged rather than deleting it blindly.

## Immutable template versions

### `storecalc.template_versions`

```text
id bigint identity primary key
template_id bigint not null references storecalc.templates(id) on delete cascade
version_number integer not null
content_state text not null
currency_code text not null
source_effective_date date
source_published_date date
created_by_user_id bigint references public.users(id) on delete set null
based_on_version_id bigint references storecalc.template_versions(id)
created_at timestamptz not null
sealed_at timestamptz
content_hash text
unique (template_id, version_number)
```

`content_state` is draft or sealed.

Draft rows and their children may be changed only by their authorized owner/contributor. Submission seals the version in one transaction, calculates a canonical content hash, and permanently blocks content updates and deletes.

A database trigger should reject changes to sealed version content and child rows. Lifecycle and confidence state live outside the immutable content tables.

### `storecalc.version_categories`

Snapshot of category presentation in one version.

```text
id bigint identity primary key
version_id bigint not null references storecalc.template_versions(id) on delete cascade
category_id bigint not null references storecalc.template_categories(id)
display_name text not null
description text
sort_order integer not null
active boolean not null
unique (version_id, category_id)
```

### `storecalc.version_spending_buckets`

```text
id bigint identity primary key
version_id bigint not null references storecalc.template_versions(id) on delete cascade
stable_key text not null
display_name text not null
is_primary boolean not null default false
limit_minor bigint
sort_order integer not null
unique (version_id, stable_key)
```

Checks:

- limits are nonnegative;
- each version has exactly one primary bucket once sealed;
- a null limit means unlimited, not unknown;
- unknown limits must be represented by a version warning/assessment rather than silently treated as unlimited.

### `storecalc.version_items`

Authoritative item snapshot for a version.

```text
id bigint identity primary key
version_id bigint not null references storecalc.template_versions(id) on delete cascade
item_id bigint not null references storecalc.template_items(id)
category_version_id bigint references storecalc.version_categories(id)
spending_bucket_id bigint not null references storecalc.version_spending_buckets(id)
sku text
display_name text not null
description text
unit_label text
price_minor bigint not null
quantity_min integer not null default 0
quantity_max integer
quantity_step integer not null default 1
availability_status text not null
sort_order integer not null
unique (version_id, item_id)
```

Checks enforce nonnegative price and quantities, positive steps, and `quantity_max >= quantity_min` when present.

`availability_status` initially allows available, blocked, and informational. A blocked item remains visible when useful but cannot be added.

### `storecalc.version_tax_rules`

```text
id bigint identity primary key
version_id bigint not null references storecalc.template_versions(id) on delete cascade
scope_type text not null
category_version_id bigint references storecalc.version_categories(id)
item_version_id bigint references storecalc.version_items(id)
rate_ppm integer not null
rounding_mode text not null
price_includes_tax boolean not null default false
priority integer not null
created_at timestamptz not null
```

Checks enforce exactly one compatible scope target:

- template scope has neither category nor item target;
- category scope has a category target only;
- item scope has an item target only.

The calculator resolves the most specific matching rule and rejects ambiguous equal-priority rules.

### Additional rules

Eligibility and unusual facility rules may begin in a bounded table:

```text
storecalc.version_rules
id
version_id
rule_type
scope_type
category_version_id
item_version_id
rule_payload jsonb
priority
```

Every supported `rule_type` has an explicit application validator and versioned payload schema. Unknown rule types fail closed rather than being ignored.

## Publication and active-version history

Do not store a mutable `active` flag directly on immutable version content.

### `storecalc.template_publications`

```text
id bigint identity primary key
template_id bigint not null references storecalc.templates(id)
version_id bigint not null references storecalc.template_versions(id)
started_at timestamptz not null
ended_at timestamptz
published_by_user_id bigint references public.users(id) on delete set null
reason text not null
```

A partial unique index permits only one publication row with `ended_at IS NULL` per template.

Promotion happens transactionally:

1. verify the candidate version is sealed and belongs to the template;
2. end the current publication, if any;
3. insert the new current publication;
4. append state and audit events;
5. preserve all prior publication periods.

### `storecalc.version_state_events`

Append-only lifecycle history:

```text
id bigint identity primary key
version_id bigint not null references storecalc.template_versions(id)
state text not null
reason text
actor_user_id bigint references public.users(id) on delete set null
created_at timestamptz not null
```

States may include unverified, source_backed, community_confirmed, disputed, stale, and archived.

The current display state is derived from the newest valid event or maintained in a rebuildable projection table. State events never mutate version content.

### `storecalc.version_assessments`

Stores explainable confidence calculations.

```text
id bigint identity primary key
version_id bigint not null references storecalc.template_versions(id)
algorithm_version text not null
score integer not null
label text not null
factors jsonb not null
generated_at timestamptz not null
superseded_at timestamptz
```

Confidence is advisory and explainable. It never grants a user a global role or deletes competing evidence.

```text
facility_id bigint not null references storecalc.facilities(id)
```

The server recalculates and validates every saved mutation. Client-submitted totals are never authoritative.


Structured reasons use a child table parallel to proposal review reasons.

## Ownership and account deletion

Account deletion requires an explicit data-classification policy.

### Delete with the account

- private provisional facilities owned only by the user, unless shared references require a reviewed transfer;
- private store programs and private templates owned only by the user;
- draft template versions not submitted publicly;
- private raw uploads and extraction drafts;
- saved orders and order items;
- follows, current-facility settings, notification preferences, and notifications;
- unused recovery tokens and open support notes not required for security/audit retention.

### Preserve with creator anonymized

- accepted canonical public facility facts;
- published public templates and immutable versions;
- evidence that was explicitly approved for public factual use and contains no personal information;
- structured proposal/review outcomes required to explain version history;
- administrative audit events, subject to bounded retention and redaction;
- publication and state history.

Creator/reviewer foreign keys use `ON DELETE SET NULL` where factual integrity must survive account deletion.

### Delete or redact free text

- private support notes beyond required retention;
- proposal comments and correction explanations that are not needed to preserve a public decision;
- original filenames and metadata that could identify the user;
- private upload artifacts.

The deletion service should classify rows explicitly rather than relying on a blanket cascade from `public.users`.

Before StoreCalc persistence launches, `deleteUserYouListData` must be replaced or extended with a transactionally tested account-deletion service covering every StoreCalc ownership class. The service must prove another user's data remains untouched.

## Index plan

Initial indexes should support actual workflows rather than indexing every column.

Likely indexes include:

- lowercased facility official names and aliases by country;
- facilities by country, jurisdiction, agency, scope, owner, and status;
- store programs by facility and scope;
- templates by program, visibility, owner, and status;
- template versions by template and descending version number;
- current publication partial unique index per template;
- version items by version, category, sort order, and lowercased display name;
- orders by user and descending update time;
- proposals by template, status, and submission time;
- reviews by proposal and verdict;
- open correction reports by version;
- unread notifications by user and creation time;
- support cases by target user and open status;
- audit events by target user, actor, action type, and time.

Search behavior should be measured before adding trigram or full-text indexes. New extensions require a separate operational review.

## Transaction boundaries

The following operations must be atomic:

- seal a template version and all child content;
- submit a proposal with canonical diff/hash;
- promote a new active publication and close the prior publication;
- merge duplicate facilities and reassign allowed child records;
- save/recalculate an order and all order lines/bucket totals;
- resolve a correction report through a replacement proposal;
- owner-assisted email/account recovery, session invalidation, token revocation, notification, and audit event;
- account deletion across private data, anonymized public contributions, and sessions.

External email or object-storage deletion may occur after commit through a durable outbox/job pattern. Database state must record pending follow-up rather than holding a transaction open across network calls.

## Migration sequence

### Migration A: account-support foundation

- add bounded account-status/last-login fields if approved;
- create account support cases;
- create hashed recovery tokens;
- create append-only admin audit events;
- add indexes and triggers;
- do not yet expose owner mutation routes.

### Migration B: StoreCalc namespace and directory

- create `storecalc` schema;
- countries, jurisdictions, agencies;
- facilities, aliases, sources;
- facility requests and supporters;
- store programs;
- no template/order data yet.

### Migration C: template identity and immutable versions

- templates;
- stable categories/items;
- versions and snapshot children;
- spending buckets, tax rules, bounded rules;
- publication and state history;
- immutability triggers.

### Migration D: private user workflow and orders

- user settings and follows;
- orders, order items, bucket totals;
- calculation snapshots;
- extend account deletion tests before enabling persistence.

### Migration E: uploads and contribution workflow

- uploads, extraction drafts, evidence;
- proposals and diffs;
- reviews, reasons, correction reports, comments;
- content/privacy reports.

### Migration F: notifications and confidence

- notifications and preferences;
- assessments and derived scoped contributor statistics;
- review queue indexes and owner exception views.

Each migration should be small enough to rehearse, verify, and roll forward independently. Large table creation does not justify combining unrelated application behavior in the same PR.

## Migration execution and rollback

### Before production

For every executable migration:

1. verify the exact merged commit and migration checksum;
2. create and verify a fresh off-VM backup;
3. restore into a disposable PostgreSQL instance;
4. apply the migration;
5. run schema, constraint, ownership, and application tests;
6. exercise rollback on the disposable database when rollback is safe;
7. verify the original fingerprint after rollback;
8. document estimated lock behavior and expected runtime.

### Initial empty-table rollback

Before StoreCalc stores production data, a failed migration may drop only the newly created empty tables/schema in strict reverse dependency order.

### After live data exists

Do not use destructive down migrations that erase real StoreCalc data. Prefer a forward corrective migration, disable the new application path, and restore only from a verified backup when no safe forward repair exists.

### Existing Ops limitation

The current controlled Ops migration worker supports a narrow allowlisted index operation, not these schema migrations. StoreCalc schema deployment requires either:

- a separately reviewed expansion of the controlled migration capability to exact repository-owned migrations; or
- a bounded manually supervised migration run following the same backup, rehearsal, checksum, transaction, and verification requirements.

Do not smuggle schema SQL through a generic Ops action.

## Verification requirements

Schema tests must prove:

- private facilities/templates/orders cannot be read or mutated by another user;
- a public template version cannot be edited after sealing;
- only one active publication exists per template;
- an active publication references a sealed version belonging to the same template;
- historical orders remain unchanged after a new version is published;
- money and tax fields reject invalid values;
- item/category/version relationships cannot cross templates;
- a needs-correction review has structured reasons;
- duplicate review/support rows are rejected;
- facility merges preserve attached history without cross-user leakage;
- account deletion removes private data, anonymizes preserved public facts, invalidates sessions, and leaves unrelated users untouched;
- owner recovery records an audit event and never stores the raw token;
- audit events cannot be updated or deleted through normal application credentials;
- raw upload keys and private evidence cannot be enumerated through public routes.

## Decisions deliberately deferred

- exact OCR/document extraction provider;
- object-storage provider and retention duration;
- public order-sharing design;
- general RBAC beyond current user/admin roles;
- database row-level security;
- trigram/full-text search extensions;
- automatic official-source import staging tables;
- international tax formats beyond the rate/rounding model;
- support-session impersonation;
- partitioning or archival tables before volume justifies them.

These decisions must not block the first directory, calculation, and immutable-version slices, but the schema leaves clear extension points for them.
